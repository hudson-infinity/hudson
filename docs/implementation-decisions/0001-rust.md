# 0001: Rust implementation with language-neutral interfaces

- Status: Accepted
- Date: 2026-09-18
- Scope: Hudson's core implementation language and integration boundaries

## Context

Hudson is an open-source-first platform for building, running, securing, observing, and evaluating AI agents. We want one core implementation language while allowing customers to use Hudson from applications and tools written in their preferred languages.

The platform is still in product and architecture design. This decision records the chosen direction; it does not indicate that the runtime or interfaces have been implemented.

## Decision

Use **Rust** as the implementation language for Hudson's core:

- Agent runtime and default harness
- API, background workers, and CLI
- Permission enforcement, approvals, and budget controls
- Execution records and observability
- Evaluation orchestration and built-in evaluators

Keep customer-facing integration contracts language-neutral. Applications should be able to create runs, inspect progress, handle approvals, cancel execution, and retrieve results without running Rust code in their own process.

## Why Rust

Rust offers ahead-of-time compilation, memory safety through its ownership system, and control over data layout and resource use. These properties fit the intended infrastructure product and provide room to optimize execution components as workloads grow.

This is a deliberate engineering choice, not a claim that Hudson's current requirements cannot be implemented in Python or Go. Performance benefits depend on the workload and must be measured. Faster local execution does not make a remote model provider respond faster.

The choice also carries costs: Rust's ownership model, asynchronous code, and library integration require expertise, and some integrations may take more work than they would in Python.

See the Rust documentation on [compilation](https://doc.rust-lang.org/book/ch01-02-hello-world.html), [ownership](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html), and [data layout](https://doc.rust-lang.org/reference/type-layout.html).

## How other languages use Hudson

The initial interface direction is a versioned HTTP API with JSON messages and an OpenAPI description. Event streaming should expose run progress. Exact endpoints, streaming behavior, and compatibility rules remain to be designed.

```text
Customer application (Python, JavaScript, Java, Go, etc.)
    |
    | HTTP requests and structured responses
    v
Hudson server (Rust)
    |
    | Permission-checked tool requests
    v
Customer tool endpoint or worker (any supported language)
```

Language-specific SDKs may provide convenient wrappers around the API. They must not duplicate the runtime, harness, or authorization logic. SDKs can contain generated code and small language-specific helpers; they still require compatibility tests and maintenance.

Customers should also be able to supply tools through authenticated HTTP endpoints or workers using a documented protocol. A Python tool runs in a Python process and returns structured results to Hudson. Custom harnesses and evaluators should follow similarly explicit extension contracts.

Local development, self-hosting, and managed hosting should expose the same public contracts. Connecting to a local Rust server should follow the same application flow as connecting to a hosted instance.

## Security boundary

Rust's memory-safety properties do not implement authorization, tenant isolation, or sandboxing. Those controls must be designed and enforced separately.

Hudson must authorize operations before dispatch, validate arguments, bind approvals to specific actions, constrain credentials, and record execution evidence. Customer code hosted by Hudson must be isolated so it cannot bypass the permitted execution paths.

For customer-operated services, Hudson controls the invocations it sends. It cannot govern unrelated actions those services perform using their own access.

Unsafe Rust and native dependencies require particular care. The implementation language is one part of the security design.

The subsequent [external sandbox decision](0002-hudson-sandbox.md) assigns isolated execution to the separate [Hudson Sandbox repository](https://github.com/hudson-infinity/hudson-sandbox). Hudson retains authority over agent runs, permissions, approvals, credentials, and budgets.

## Still to decide
